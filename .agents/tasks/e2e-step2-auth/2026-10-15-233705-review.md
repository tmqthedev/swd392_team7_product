# Step 2 auth: scrypt + HMAC-JWT sessions, admin domain, real email, and the real frontend session

The branch delivers the full Step 2 auth surface against the plan: a scrypt password hasher and a hand-rolled HMAC-SHA256 JWS token service (no bcrypt, no JWT library), access/refresh cookies that are httpOnly with env-driven Secure and SameSite=Lax, server-side refresh sessions stored as `sha256(token)` in `auth_session` and rotated on every refresh, login lockout after a configurable failure threshold, enumeration-safe forgot/reset with single-use tokens that revoke all sessions on consumption, an Origin-based CSRF guard, role and subject-scope middleware, the admin domain (user management, all-or-nothing Excel student import, subject CRUD, lecturer assignment), a real nodemailer SEND_EMAIL job handler, a create-admin CLI, and a frontend that replaces the mock AuthContext with a real `/auth/me` session plus the admin UI. I ran all four verification commands: backend `npm test` (74/74), `npm run test:e2e` (exit 0, 2 Postgres suites self-skip), frontend `npm run build` (exit 0), and `npm run lint` (exit 0, warnings only). **Verdict**: APPROVED

## High-level view

The crypto foundation matches the mandate exactly. Passwords use `crypto.scrypt` with a per-user salt stored as `scrypt$N$r$p$salt$hash` and verified with `timingSafeEqual`; there is no bcrypt anywhere. Tokens are a compact HS256 JWS built from Node `crypto`, carrying `{sub, role, type, iat, exp, jti}`, verified with a constant-time signature compare plus expiry and type checks. Access and refresh tokens ride in httpOnly cookies whose `secure`/`sameSite` come from env (`Lax` default), and the refresh token is only ever persisted as its sha256 in `auth_session`.

The session lifecycle is fail-closed. Refresh verifies the JWT, requires a matching active (non-revoked, unexpired) session row, then revokes the old row before minting a new pair, so a replayed refresh token is rejected. Reset/set consume a single-use token and revoke every session for the user; change-password keeps only the caller's current session. Forgot-password returns an identical shape whether or not the account exists and only enqueues mail when it does.

Authorization is centralized: `requireAuth` reads the access cookie (Bearer fallback), `requireRole` denies 403 on mismatch, and `requireSubjectScope` lets ADMIN through, requires a LECTURER to be assigned to the subject, and denies everyone else. The Origin/CSRF guard rejects state-changing requests whose Origin is absent or not in the allow-list, with a deliberate no-op when no origins are configured (test harness).

The admin domain enforces the all-or-nothing import contract: the whole workbook is validated (required fields, email format, in-file and DB duplicates) before any write, and a single bad row yields `422` with per-row errors and zero inserts/zero emails. Email flows through a real nodemailer transport behind the SEND_EMAIL job, which rethrows on failure so the queue retries; no plaintext password ever enters a payload — account setup is always a single-use link. The frontend removes the mock role-picker and fake context, resolves the session from `/auth/me`, guards routes by uppercase server role, and adds the admin UI.

Two minor behavioral notes, both confirmed and neither blocking: the lockout rolling window is measured from `updated_at`, a column every `update()` bumps, so an unrelated admin edit resets the window basis; and the import loops per row with multiple DB round-trips under only a 10mb body cap.

<summary>Details</summary>

### scrypt and HMAC-JWS, no external crypto deps

`passwordHasher` uses `crypto.scrypt` (N=16384, r=8, p=1, 64-byte key, 16-byte random salt) encoded as `scrypt$N$r$p$saltB64$hashB64`, verifies with `timingSafeEqual`, and `assertStrong` rejects passwords under 8 chars with a 400. `tokenService` hand-rolls HS256: `base64url(header).base64url(payload).base64url(hmac)`, verify splits into three segments, recomputes the signature, compares constant-time, parses the payload, and enforces `exp` and optional `type`. The dependency list carries no bcrypt and no `jsonwebtoken`, matching the plan's rationale comment. Both modules are covered by round-trip, tamper, expiry, and wrong-type tests.

### Fail-closed refresh rotation

`refresh` verifies the refresh JWT, looks up the active session by `sha256(token)`, confirms the user is present and not LOCKED, revokes the old session, and mints a fresh pair. A replayed old token no longer matches an active row and is rejected 401 — asserted directly in `authService.test.js` (old hash gone, new hash active, reuse throws). `logout` is idempotent, and reset/set/change all revoke sessions appropriately (`revokeAllForUser` on reset/set; `revokeAllForUser({exceptHash})` on change to keep the caller signed in).

### Lockout window coupling

`_registerFailure` computes `withinWindow` by comparing `now - new Date(user.updated_at)` against `loginWindowMinutes`. Because `appUserRepository.update()` always appends `updated_at = now()`, the "last failure" timestamp is really "last write of any kind." An admin editing the user, or an unlock, between failed attempts resets the window basis. The failure path itself is the common case and works (the test drives 5 consecutive failures to a 423 lock), and a successful login zeroes the counter, so the coupling only ever makes lockout slightly more lenient — never bypasses an active `locked_until`. A dedicated `last_failed_login_at` would decouple it cleanly. Confirmed, minor.

### Enumeration-safe recovery with single-use tokens

`forgotPassword` returns `{ok:true}` for both known and unknown identifiers and only invalidates prior RESET tokens, creates a new one, and enqueues mail when the user exists — asserted by `deepEqual(unknown, known)` and a single enqueued job. `_consumePasswordToken` requires an active (unused, unexpired) token for the right purpose, sets the new hash, marks the token used, and revokes all sessions; reuse of a consumed token returns 400 (asserted). The raw token lives only in the emailed link; the DB stores `sha256(raw)`.

### Authorization and Origin guard

`createAuthMiddleware` exposes `requireAuth` (access cookie or `Authorization: Bearer` fallback), `requireRole(...roles)` (accepts spread or array), and `requireSubjectScope` (ADMIN bypass, LECTURER must appear in `listSubjectIdsForLecturer`, else 403; non-integer subject id → 400). `verifyOrigin` passes GET/HEAD/OPTIONS, enforces an allow-list derived from `env.appBaseUrl` on state-changing methods, and no-ops only when the list is empty — which is the documented test-harness path, not a production path (real deploys always set `APP_BASE_URL`). This is the one area the plan explicitly flags for live verification: whether the frontend's same-origin writes behind nginx are allowed while cross-origin writes are rejected still needs a running stack to confirm, as the FEAT-003 findings note.

### All-or-nothing Excel import

`importStudents` parses the workbook with exceljs, resolving the three columns by substring match on the header row (order-tolerant), skips fully blank rows, then runs two validation passes — in-file shape/duplicates, then DB duplicates — collecting `{row, errors[]}` before writing anything. Any error short-circuits to `{ok:false, errors}` with zero inserts and zero email enqueues; only a fully clean file inserts every STUDENT and enqueues one SET email each. The controller maps `ok:false` to 422 and success to 201. The all-or-nothing invariant is asserted in `adminService.test.js`. The per-row loop (two lookups + insert + enqueue each) is unbounded beyond the 10mb raw-body cap — acceptable for class sizes, worth a row cap or batched lookups if larger uploads are expected. Confirmed, minor.

### Real email via the SEND_EMAIL job

`createEmailService` builds a lazy nodemailer SMTP transport (auth only when `smtpUser` is set, so Mailpit needs none) and renders SET/RESET bodies that embed only the one-time link. `registerDefaultHandlers` wires a real SEND_EMAIL handler that renders from `template`+`variables.link` when `html/text` are absent, calls `sendMail`, and rethrows on failure so the queue retries; the other three job types stay stubs, and SEND_EMAIL falls back to a no-op in mock mode. `server.js` constructs the service and queue only against a real DB. Payload mapping and retry-on-throw are asserted with a fake emailService.

### Frontend real session

`AuthContext` fetches `/auth/me` on mount, exposes `{user, loading, login, logout, refresh}`, and stores the server user with its uppercase role; the mock role-picker and fake context are gone. `ProtectedRoute` holds a loading state until `/auth/me` resolves, redirects unauthenticated users to `/`, and sends role mismatches to their own home. `authApi`/`adminApi` always send `credentials:'include'`. Login surfaces 423 as a lock message and other failures as generic invalid-credentials. The `/admin` group is guarded for ADMIN with users and subjects pages, including the per-row import error table. `config/api.js` reads `import.meta.env.VITE_API_BASE_URL` with a localhost fallback.

### Migration and verification

`011_auth_step2.sql` only `ADD COLUMN IF NOT EXISTS` on `app_user` (`must_change_password`, `updated_at`) and two `CREATE INDEX IF NOT EXISTS`, recreating nothing from 004 — idempotent and correctly ordered after 010.
