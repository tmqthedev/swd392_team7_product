# E2E Step 1 foundation: unified data model, migration runner, job queue, local stack

Step 1 lays the local-dev and database foundation for the viva platform: it extends `env.js` with the full Step-1 variable surface, adds an auto-running migration runner that builds the entire unified data model (23 new tables plus pgvector and an HNSW index) on top of the existing baseline, migrates legacy `question.status` values and relaxes the CHECK, adds nine repositories in the existing style plus a Postgres-backed `background_job` queue using `FOR UPDATE SKIP LOCKED` with retry/backoff and no-op stub handlers, and ships a repo-root `docker-compose.yml` + `nginx.conf` + `.env.example`. No business logic from later steps is implemented. Watch for: nothing blocking — a stale note in the FEAT records claims `npm run test:e2e` fails in the worktree, but the jest glob was actually fixed and it now passes (confirmed, minor).

**Verdict**: APPROVED

## High-level view

The migration runner reuses `PgDatabase.pool` rather than opening a second pool, tracks applied versions in `schema_migrations`, and runs each pending numbered file in its own transaction so re-runs are no-ops. It runs from `server.js` before `app.listen`, gated to `!env.dbMockMode` and only when the db exposes a `.pool`, so mock mode and test injection are untouched. The legacy status migration (007) updates `Active->APPROVED` and `Draft->DRAFT` before dropping and re-adding the CHECK, so the ordering is safe on an existing database and a no-op on a fresh one.

The `background_job` queue claims work with an `UPDATE ... WHERE id = (SELECT ... FOR UPDATE SKIP LOCKED LIMIT 1)` inside a transaction, so concurrent workers never grab the same row. Failures re-queue as PENDING with an exponential `run_after` backoff until `attempts` reaches `max_attempts`, then settle as FAILED. Handlers for all four job types are log-and-succeed stubs, correctly deferring real logic to later steps.

The compose stack defines backend, postgres (pgvector pg16), dynamodb, minio, mailpit, and nginx; `stt` is a commented placeholder that nothing `depends_on`, so `docker compose up` never blocks on a missing Step-9 image. Behavior differs from prod only by env values — there are no `if (local)` branches anywhere in `src`.

Test gating works as designed: pure-logic suites are named `*Service.test.js` and run under `npm test`; Postgres-dependent suites are `*.e2e.test.js` and self-skip when `TEST_DATABASE_URL`/`DATABASE_URL` is unset, so both `npm test` and `npm run test:e2e` stay green without Docker.

### Migration runner reuses the pool and is startup-gated

`runMigrations({ pool, dir, logger })` takes the pool in rather than constructing one, ensures `schema_migrations(version TEXT PK, applied_at)`, orders files by numeric prefix (`orderMigrationFiles` sorts 001 < 002 < 010 and drops non-`NNN_` files), and applies each pending file plus its version INSERT inside one BEGIN/COMMIT with ROLLBACK-and-rethrow on error. `server.js` builds the db via `createDatabase(env)` only when `!env.dbMockMode`, runs migrations only when `database.pool` exists (real `PgDatabase`), then hands the same instance to `createApp({ database })` so no second pool is opened. `createApp` is untouched, keeping mock mode and test injection unaffected. The pure `orderMigrationFiles`/`pendingMigrations` helpers are exercised by `migrationRunnerService.test.js` without a DB.

### Legacy question.status migration ordering

007 performs the data migration (`UPDATE ... status='APPROVED' WHERE status='Active'`, `'DRAFT' WHERE 'Draft'`) before `DROP CONSTRAINT IF EXISTS chk_question_status` and re-adding the relaxed CHECK (`DRAFT/PENDING_REVIEW/APPROVED/REJECTED/ARCHIVED`). The 001 baseline still carries the original `('Active','Draft')` CHECK, so a DB bootstrapped purely by the runner starts with the old constraint and 007 relaxes it — the sequence is correct whether the database is fresh or pre-populated.

### Background job claim is exclusive under contention

```sql
UPDATE background_job
SET status='RUNNING', locked_at=now(), attempts=attempts+1, updated_at=now()
WHERE background_job_id = (
  SELECT background_job_id FROM background_job
  WHERE status='PENDING' AND run_after<=now()
  ORDER BY run_after FOR UPDATE SKIP LOCKED LIMIT 1
) RETURNING *
```

`claimNext` runs on a transaction client passed from `JobQueue._claim`, so the row lock from `FOR UPDATE SKIP LOCKED` is held for the claim and concurrent workers take distinct rows. `markFailed(id, msg, nextRunAfter)` branches on whether `nextRunAfter` is null: non-null re-queues as PENDING with the new `run_after`; null leaves the job FAILED. `_handleFailure` chooses between them by comparing `job.attempts` to `max_attempts`, computing the delay with the pure `computeBackoffMs(attempt, base, cap) = min(base * 2^(attempt-1), cap)`. The queue's bounded loop keeps at most `env.jobQueueConcurrency` jobs in flight and `stop()` awaits in-flight settles.

### Compose stack and stt placeholder

nginx publishes 8080 and proxies to `backend:3000` (backend `expose: 3000`), postgres is `pgvector/pgvector:pg16` with a `pg_isready` healthcheck that `backend` waits on, and dynamodb/minio/mailpit are wired to the endpoints `env.js` reads. The `stt` block is commented out and nothing depends on it; `LAMBDA_ENDPOINT=http://stt:8080` is pre-wired so uncommenting the block in Step 9 is the only change needed. `docker compose config --quiet` parses cleanly.
